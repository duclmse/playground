# Benchmark report

Generated by `scripts/benchmark.sh --export-markdown benchmarks/RESULTS.md`
on 2026-09-08 (two runs: M1 baseline, then M2 after
`docs/fastlua-roadmap.md`'s M2 work landed). See `benchmarks/README.md` for
methodology (hyperfine, warmup + ≥10 runs per command, whole-process wall
time) and what each script exercises.

## M2 vs. M1: an honest result - the optimizations are real, but didn't move these two benchmarks

M2 added (docs/fastlua-roadmap.md): `opt_level = "speed"` (turns on
Cranelift's own mid-end passes, previously running at `"none"`), array
bounds checking (a correctness fix - M1 had *none*), a narrow bounds-check
elimination pattern, AST-level constant folding, and function inlining -
all verified correct by 21 passing tests (`cargo test -p fastlua`).

| Benchmark | fastlua (M1, no checks) | fastlua (M2, checked + optimized) |
|---|---:|---:|
| fib | 13.3 ms | 15.1 ms |
| table_array | 16.3 ms | 15.6 ms |

Both deltas are inside the noise (σ ≈ 3 ms on ~15 ms means). Two honest,
verified reasons this isn't a regression hiding in the noise, and why M2's
work is real despite not showing up here:

1. **The bounds check itself is nearly free on these workloads.** Directly
   compared (not in this table): a hand-written `table_array` variant using
   the exact `for i = 0, #a - 1` pattern the elimination pass matches ran
   at 16.1 ms, against 14.2 ms for the actual benchmark's `for i = 0, n - 1`
   form (`n` a plain local) that the pattern does *not* match and so keeps
   its check - statistically indistinguishable. `table_array` moves 32MB
   through memory (4M × 8 bytes, twice); it's memory-bandwidth-bound, not
   branch-bound, so a single well-predicted bounds check per iteration is
   lost in the noise regardless of whether it's eliminated. Bounds-check
   elimination's real payoff shows up on compute-bound loops, or as an
   *enabler* for vectorization (M7) - a trap can't be vectorized across,
   a proven-safe loop can.
2. **Neither benchmark exercises inlining.** `fib` is self-recursive
   (correctly excluded from inlining - see `is_directly_recursive`);
   `table_array`'s `main` makes no calls to inline. Inlining *is* verified
   working (`tests/fixtures/inlining.fl`, `bool_logic.fl`,
   `sum_array.fl`'s call to `sum`), just not by a workload in this
   benchmark set. A function-call-heavy benchmark (§33's `03_function_calls`
   category - not yet in `benchmarks/`) would be the honest way to measure
   this pass's impact instead of inferring it from workloads that don't
   use it.

Constant folding is similarly unexercised here (neither program has a
compile-time-foldable expression in its hot path) but is verified correct
by `optimize.rs`'s own unit tests.

**Net effect of M2 so far**: a real correctness fix (bounds checking) shipped
at effectively zero measured cost, plus three optimizer passes that are
implemented and tested but don't yet have a benchmark that shows their
value - a gap for M2/M7 benchmark-suite work to close, not a reason to
doubt the passes themselves.

## M4 (GC): a new, honest weak spot - allocation churn

M4 (docs/fastlua-roadmap.md) replaced M1-M3's leak-everything runtime with
a real collector (`crates/fastlua/src/gc.rs`) - see that file's doc
comment for the scope call: conservative (stack-scanning) mark-sweep,
single generation, one `std::alloc`-backed block per allocation, not the
originally-sketched generational/bump-allocated design. `benchmarks/
gc_alloc.{lua,fl}` is the new, dedicated allocation-churn benchmark this
milestone's checklist asks for (§33's `08_gc` category) - a fresh,
immediately-discarded 2-field object every iteration, 2,000,000
iterations, nothing else.

| Command | Mean [ms] | Min [ms] | Max [ms] | Relative |
|:---|---:|---:|---:|---:|
| `lua (reference)` | 202.4 ± 9.4 | 193.0 | 224.8 | 13.03 ± 3.27 |
| `luajit` | 15.5 ± 3.8 | 11.9 | 38.6 | 1.00 |
| `vm (this project)` | 490.8 ± 16.2 | 480.3 | 523.2 | 31.58 ± 7.85 |
| `fastlua` | 123.1 ± 2.8 | 119.8 | 129.7 | 7.92 ± 1.96 |

**This is a genuinely different result from `fib`/`table_array` above**,
and worth stating plainly rather than burying: fastlua still beats
reference Lua (1.6×) and this project's own dynamic VM (4×) here, but for
the first time **loses to LuaJIT** (7.9× slower), on the one workload
shape M4 introduced a real cost for. Two understood, expected reasons -
this is the collector working as designed, not a bug:

1. **Every collection is a full heap walk.** `gc.rs` is deliberately
   single-generation mark-sweep (see its doc comment for why generational
   pacing was descoped) - there's no young-generation fast path that
   avoids rescanning long-lived data, so at steady state each of the many
   collections this benchmark triggers re-marks the *entire* live set, not
   just what changed since the last one. LuaJIT's generational GC (and
   even reference Lua's incremental one) specifically avoids this.
2. **Per-block bookkeeping overhead.** Every allocation is a `HashMap`
   insert/lookup rather than a bump-pointer increment - the roadmap's
   bump-allocated-arena item (deferred, see `gc.rs`) would remove this
   entirely for the common case.

Both are the exact throughput costs the roadmap's deferred items (bump
allocation, generational young/old split) exist to fix - this benchmark
is what will show whether a future pass on those actually moves the
number, the same honest, falsifiable-check role `table_array` played for
M2's bounds-check elimination.
